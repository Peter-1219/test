# 滲透測試基礎筆記：範圍、風險、測試思維與職業倫理

> 本筆記依照課程 Task 1～7 的畫面內容重新編排，並補充實務判斷方式、比較表、工作文件與複習題。本文只討論合法、經書面授權的安全評估；沒有授權、超出範圍或忽略停止條件的測試，都不屬於專業滲透測試。

## 一、課程定位與學習目標

滲透測試（penetration testing，常簡稱 **pentesting**）是一種主動式安全評估。測試人員會在明確授權和約定邊界內，以攻擊者可能採用的思路驗證系統、應用程式或網路是否存在可被實際利用的弱點，並把技術結果轉化成組織可以採取行動的風險資訊。

完成本主題後，應能：

1. 從授權、範圍、涵蓋程度與責任區分滲透測試和惡意入侵。
2. 說明 Web 應用程式與網路滲透測試各自關注的項目。
3. 分辨弱點（vulnerability）、威脅（threat）和風險（risk）。
4. 使用「可能性 × 衝擊」而不是只看技術名稱評估風險。
5. 說明識別、分析、降低與監控的風險管理循環。
6. 辨認弱點形成的常見根因，而不只記住弱點名稱。
7. 採取有系統、重視證據及商業情境的測試思維。
8. 在整個專案中遵守倫理、權限、範圍和信任原則。

## 二、什麼是滲透測試？

### 1. 定義與目的

滲透測試是由系統擁有者明確允許、在事前同意的限制內執行的安全評估。它不是單純執行掃描器，也不是以「成功入侵」作為唯一目標，而是要回答：

- 哪些攻擊面真的存在？
- 弱點是否可被利用，利用條件是什麼？
- 弱點組合後可能造成什麼實際影響？
- 現有控制能否偵測、阻擋或限制攻擊？
- 組織應優先修正什麼，以及如何驗證修正成果？

現代系統會持續更新，並由程式碼、雲端服務、API、第三方元件、身分系統與網路設備共同組成。設計審查、程式碼審查和自動掃描都很重要，但無法單獨涵蓋所有錯誤組合。滲透測試的價值在於模擬真實使用路徑、驗證控制間的落差，並用可重現的證據呈現風險。

### 2. 滲透測試可以帶來什麼價值？

- 依可利用性與業務衝擊排列修補優先順序。
- 找出單一工具不易發現的邏輯漏洞和弱點鏈。
- 評估敏感資料，例如個人識別資訊（PII）或付款資訊的保護程度。
- 協助驗證組織政策、產業標準或法規控制是否有效；但一次滲透測試本身不等於完整合規。
- 向管理者、客戶及其他利害關係人提供控制有效性的合理保證。
- 為後續修補驗證、偵測規則與安全設計改善提供依據。

### 3. 滲透測試不等於什麼？

| 活動 | 主要目的 | 和滲透測試的差異 |
| --- | --- | --- |
| 弱點掃描 | 自動找出已知版本或設定問題 | 通常不深入驗證利用和業務影響 |
| 弱點評估 | 識別、確認並排列大量弱點 | 比滲透測試更重視廣泛盤點，利用通常較受限 |
| 程式碼審查 | 從原始碼找安全缺陷 | 不一定驗證部署後的端到端攻擊路徑 |
| 紅隊演練 | 測試人員、流程與技術的整體偵測／應變 | 目標導向且可能更隱蔽，通常不追求逐項完整覆蓋 |
| Bug bounty | 讓外部研究者依政策回報弱點 | 範圍與獎勵由長期方案規定，不等於固定時程的委託案 |

不同活動可以互補。不能因掃描器顯示「沒有高風險」就宣稱系統安全，也不能因滲透測試時間內沒有成功利用，就證明不存在弱點。

## 三、滲透測試與惡意入侵的差異

兩者可能使用相似工具或技術，但**是否合法及專業，取決於授權、目的、邊界和行為，而不是工具名稱**。

| 核心因素 | 滲透測試人員 | 惡意攻擊者 |
| --- | --- | --- |
| 授權 | 取得系統擁有者的明確書面同意 | 未經同意存取或破壞系統 |
| 範圍 | 遵守指定資產、帳號、時段和技術限制 | 不受客戶核准範圍約束 |
| 涵蓋程度 | 依測試計畫廣泛評估多個區域 | 常選擇最快、最有價值的成功路徑 |
| 目的 | 識別風險、提出修補方式並提升防禦 | 竊取、破壞、牟利、監控或其他未授權目的 |
| 責任 | 對行動與影響負責，保存紀錄並主動溝通 | 通常逃避歸責，並可能隱藏活動 |
| 資料處理 | 只取得證明影響所需的最少資料 | 可能大量蒐集、外傳或販售資料 |
| 結束方式 | 清除測試帳號／檔案並提交報告 | 可能建立持久性以便持續進入 |

### 重要判斷情境

- 在自有測試環境操作，不表示可將同一技巧用於其他人的公開服務。
- 客戶授權測試某個網域，不一定代表其第三方 SaaS、CDN 或母公司網域也在範圍內。
- 找到可連往範圍外系統的入口時，應停止、保存最低限度證據並回報，而不是以「已經進得去」作為繼續測試的理由。
- 緊急口頭請求可能不足以改變合約範圍；應透過事先約定的變更與核准程序確認。

## 四、滲透測試的範圍與接洽規則

### 1. Scope 應寫清楚什麼？

範圍（scope）是測試邊界，至少應明列：

- **包含的資產：**IP／CIDR、網域、API、行動 App、雲端帳號或辦公地點。
- **排除的資產：**第三方系統、正式付款流程、醫療設備等不可測項目。
- **測試時窗：**日期、時區、允許高負載操作的時間及凍結期間。
- **允許與禁止手法：**例如是否允許社交工程、密碼測試、阻斷服務、實體測試或資料外傳模擬。
- **測試來源：**測試人員的固定 IP、VPN、工具主機與測試帳號。
- **資料處理：**可取得的資料量、加密方法、保存位置、保存期限和刪除方式。
- **通知與停止條件：**服務異常、接觸敏感資料、影響第三方或發現重大事件時如何處理。
- **聯絡與升級路徑：**一般窗口、緊急聯絡人、可核准範圍變更的人。

### 2. Rules of Engagement（RoE）

RoE 是把範圍轉成實際執行規則的文件。除上述項目外，常包含：

- 是否通知防守團隊，或採雙盲方式測試；
- 並行連線、請求速率和自動化工具限制；
- 測試帳號角色及可否新增帳號、檔案或排程；
- 證據截圖是否需要遮蔽個資與祕密；
- 高風險發現要立即通報，還是彙整後報告；
- 測試結束後如何清除修改、驗證服務狀態並交還資料。

若範圍不清楚，專業作法是**先停、再問、取得可追溯核准後才繼續**。

## 五、Web 應用程式滲透測試

Web 測試通常從使用者角度操作頁面與 API，評估應用程式如何處理登入、權限、工作階段、資料輸入輸出及安全設定。測試對象不只前端頁面，也可能包含後端 API、資料庫互動、檔案儲存、背景服務與第三方整合。

### 1. Authentication（身分驗證）

核心問題是「系統如何確認使用者是誰？」常見檢查方向包括：

- 密碼政策是否合理，是否阻擋已知外洩或過弱密碼；
- 登入失敗是否有適當限速，而不造成帳號鎖定型阻斷服務；
- MFA 是否涵蓋登入、復原與敏感操作，是否可繞過；
- 密碼重設連結是否短效、一次性並綁定正確帳號；
- 登入錯誤訊息是否洩漏帳號存在與否；
- 自動化攻擊防護是否兼顧安全與正常使用者體驗。

### 2. Authorization（授權與存取控制）

核心問題是「已登入者可以對哪些資源執行哪些動作？」需要同時檢查：

- **垂直權限提升：**一般使用者是否能執行管理員功能；
- **水平權限提升：**使用者 A 是否能讀取或修改使用者 B 的資料；
- 後端是否逐次驗證權限，而不是只在前端隱藏按鈕；
- API、匯出、批次功能及物件識別碼是否套用相同政策；
- 多租戶環境是否正確隔離不同客戶資料。

### 3. Session Management（工作階段管理）

工作階段讓伺服器辨認後續請求屬於哪個已登入使用者。測試重點包括：

- 工作階段識別值是否有足夠隨機性並使用安全 Cookie 屬性；
- 登入後是否重新產生識別值，防止 session fixation；
- 登出、改密碼或停用帳號後，既有工作階段是否失效；
- 是否有合理的閒置與最長存活時間；
- 敏感操作是否要求重新驗證；
- 是否有 CSRF 防護，避免瀏覽器在使用者不知情時送出狀態變更請求。

**課程情境：**使用者登出後 Cookie 仍能存取應用程式，屬於 **Session Management** 問題。

### 4. Input and Output Validation（輸入與輸出驗證）

- 在伺服器端檢查型別、長度、格式、範圍及允許值；前端檢查只能改善體驗，不能作為安全邊界。
- 資料庫查詢應使用參數化查詢，避免把輸入直接拼入 SQL。
- 輸出到 HTML、JavaScript、URL 等不同情境時，需採取相符的編碼方式。
- 上傳檔案應驗證實際內容、大小、儲存位置與執行權限，不能只相信副檔名或 `Content-Type`。
- 錯誤處理不應顯示堆疊、內部路徑、SQL 語句或祕密。

### 5. Security Configuration（安全設定）

測試項目可包含：

- TLS 與密碼學設定是否符合組織標準；
- 是否設定適當安全標頭與跨來源政策；
- 除錯模式、預設帳密、範例頁面或不必要服務是否仍開啟；
- API 是否有驗證、授權、限速與適當錯誤回應；
- 套件與伺服器版本是否受支援並完成修補；
- 祕密是否誤放在前端程式碼、版本庫、日誌或錯誤訊息中。

## 六、網路滲透測試

網路滲透測試評估連接系統的基礎設施，包括服務、主機、網路設備、遠端存取、身分機制、分段與信任關係。

### 1. External Network Penetration Test（外部網路測試）

由類似未授權網際網路使用者的角度，測試組織對外曝露的攻擊面，例如：

- 公開網站、郵件、DNS 與 VPN 閘道；
- 雲端服務、遠端管理介面和公開 API；
- 防火牆暴露的服務與不必要連接埠；
- 外部驗證、密碼政策和可被蒐集的資訊。

重點是了解沒有內部存取權的攻擊者能看到及做到什麼。課程題目中，「從未授權使用者角度測試 internet-facing infrastructure」的答案是 **External**。

### 2. Internal Network Penetration Test（內部網路測試）

常使用「假設已失陷（assumed breach）」情境，讓測試人員從內部一般端點或特定帳號開始，評估：

- 能否發現其他主機與敏感服務；
- 是否存在過度信任、共用帳密或弱驗證；
- 是否能水平或垂直提升權限；
- 網路分段和防火牆能否限制橫向移動；
- 高價值伺服器、資料庫及管理介面是否只允許必要來源；
- 監控系統能否偵測異常存取。

### 3. 網路測試的共同關注點

| 領域 | 核心問題 | 例子 |
| --- | --- | --- |
| 身分驗證 | 是否能可靠確認人與系統身分？ | MFA、密碼政策、預設帳密 |
| 授權與存取 | 是否只允許必要資源和動作？ | ACL、管理群組、信任關係 |
| 網路分段 | 一台主機失陷後能否任意擴散？ | VLAN、區段防火牆、管理網段 |
| 設定與修補 | 是否存在不安全預設或已知漏洞？ | 過時服務、弱協定、公開管理埠 |
| 監控與回應 | 惡意活動會不會被發現？ | 登入日誌、EDR、IDS／IPS、SIEM |

### 4. Web 與網路測試不是彼此獨立

Web 應用程式可能連接 API、資料庫和內部服務；外部 Web 弱點也可能成為進入內部網路的起點。因此攻擊面（attack surface）盤點必須包含元件、資料流、信任邊界和第三方相依，而不能只列 URL 或 IP。

## 七、弱點、威脅與風險

### 1. Vulnerability（弱點／漏洞）

弱點是系統、設計、流程或設定中的缺口，可能被利用而影響資料、系統或營運。弱點本身不一定立刻造成損害，例如伺服器使用含已知缺陷的舊版本軟體，但仍需要有可接觸它且具利用能力的威脅來源。

弱點可以是：

- 程式錯誤，例如未參數化的資料庫查詢；
- 設定錯誤，例如公開管理介面或雲端儲存桶；
- 設計缺陷，例如只依可預測識別碼判斷資料歸屬；
- 流程缺口，例如離職帳號沒有及時停用；
- 人員與實體控制問題，例如敏感資料處理訓練不足。

### 2. Threat（威脅）

威脅是可能利用弱點並造成傷害的來源或事件。它不一定是惡意駭客，也可能是：

- 犯罪集團、內部威脅、競爭者或國家級行動者；
- 自動化掃描與惡意工具；
- 無心的人為錯誤；
- 硬體故障、供應鏈中斷、火災或其他環境事件。

分析威脅時可考慮動機、能力、機會與目標，而不是把所有威脅視為相同。

### 3. Risk（風險）

風險是威脅成功利用弱點後，可能造成的損害。課程以概念式關係表達：

```text
Vulnerability × Threat = Risk
弱點 × 威脅 = 風險
```

這不是精確數學公式，而是提醒三者互相依賴。實務上常以以下方式討論：

```text
Risk ≈ Likelihood × Impact
風險 ≈ 發生可能性 × 影響程度
```

- **可能性：**是否對外曝露、利用難度、所需權限、現有控制與威脅活躍程度。
- **衝擊：**對機密性、完整性、可用性，以及財務、法規、營運和聲譽的影響。

### 4. 情境如何改變風險？

**低風險範例：詳細錯誤訊息**

- 弱點：錯誤頁面透露內部檔案路徑。
- 威脅：外部使用者可反覆觸發錯誤並蒐集資訊。
- 風險：資訊可協助偵察，但單獨未必能直接控制系統。

**高風險範例：失效的物件層級授權**

- 弱點：變更請求中的帳號 ID 即可讀取其他使用者資料。
- 威脅：一般已登入使用者可以列舉或修改識別碼。
- 風險：大量敏感資料外洩或遭竄改，並產生法規與商業影響。

同一類 SQL injection 出現在對外公開、處理敏感資料的正式系統，通常比出現在隔離且無敏感資料的內部測試工具風險更高。但最終仍要考慮資料、權限、可達性和補償控制，不能只用「external」或「internal」自動決定等級。

### 5. 常見評分誤區

- 把技術嚴重度直接等同業務風險。
- 只引用工具分數，沒有驗證目標環境的實際條件。
- 忽略弱點組合，例如兩個中風險問題串成帳號接管。
- 只描述最壞結果，未說明達成結果所需的前置條件。
- 因沒有公開 exploit 就判定無風險，或因存在 exploit 就一律判定最高風險。

## 八、風險管理循環與處置方式

### 1. 四個持續階段

1. **Identification（識別）：**盤點資產、弱點、威脅與既有控制。
2. **Analysis（分析）：**評估發生可能性和影響，決定風險等級與優先順序。
3. **Mitigation（降低）：**套用修補、強化存取控制、改善設定、增加監控或重新設計流程。
4. **Monitoring（監控）：**持續確認控制有效、沒有復發，並掌握新資產、新弱點和威脅變化。

組織修補測試人員回報的高嚴重度問題，屬於 **Mitigation** 階段。完成修補後仍需重新測試，並持續監控；風險管理不是修補完成便永久結束的單向流程。

### 2. 常見風險處置策略

| 策略 | 作法 | 適用思考 |
| --- | --- | --- |
| Mitigate／Reduce | 降低可能性或衝擊 | 修補漏洞、加 MFA、分段、監控 |
| Avoid | 停止帶來風險的活動 | 下架無法安全維護的功能 |
| Transfer／Share | 將部分財務或營運責任交由第三方承擔 | 保險、合約；風險不會因此消失 |
| Accept | 了解殘餘風險後正式接受 | 衝擊低或修補成本不相稱，需有核准與期限 |

接受風險不等於忽略問題，應記錄理由、風險擁有者、複審日期和觸發重新評估的條件。風險轉移也不會轉移所有責任，例如客戶信任、法規義務與營運中斷仍可能由組織承擔。

## 九、弱點為什麼會存在？

### 1. Human Assumptions（人為假設）

開發者常假定使用者會依預期方式操作，但攻擊者會刻意測試不正常輸入、順序和狀態。

**課程範例：**開發者假定大頭照欄位只會上傳圖片，沒有建立驗證和隔離措施，因而形成 unrestricted file upload。履歷上傳功能若沒有 guardrails，也屬於同類人為假設問題。

**改善方式：**明確建立濫用案例、在伺服器端驗證、採預設拒絕、限制大小與類型、重新命名檔案，並存放在不可執行且與 Web 根目錄隔離的位置。

### 2. Software Bugs（軟體錯誤）

邏輯錯誤、邊界條件、競態條件或輸入處理不完整，都可能造成非預期安全行為。

**課程範例：**將表單資料直接串接到 SQL 查詢，導致 SQL injection。

**改善方式：**參數化查詢、型別與範圍驗證、最小資料庫權限、程式碼審查、自動測試，以及在正式環境安全地處理錯誤。

### 3. System Complexity（系統複雜度）

API、微服務、資料庫、雲端權限與第三方服務形成大量互動和信任邊界，使設定錯誤更容易被忽略。

**課程範例：**多項整合服務中有管理 API 被意外公開。

**改善方式：**維護資產和資料流清單、使用一致的組態基線、集中身分政策、移除不必要端點、進行架構威脅建模並持續偵測設定漂移。

### 4. Over-Customisation（過度客製化）

自行打造登入、密碼雜湊、工作階段或帳號復原機制，可能偏離成熟框架的安全預設，也增加更新與維護成本。

**課程範例：**自製驗證流程逐漸過時，造成弱雜湊與不一致的 session timeout。

**改善方式：**優先採用維護良好的標準元件、把客製範圍降至必要程度、記錄偏離標準的原因，並為元件升級和退場建立負責人。

### 5. Technical and Design Flaws（技術與設計缺陷）

若安全沒有從設計初期納入，後加功能可能只覆蓋表面流程，卻沒有保護所有狀態或入口。

**課程範例：**系統在 MFA 完成前就發出完整驗證的 session cookie，使使用者可跳過 MFA 直接存取受保護頁面。

**改善方式：**安全設計審查、威脅建模、明確狀態機、所有伺服器端路徑的一致授權檢查，以及測試錯誤順序、中斷和重送情境。

### 6. 根因與結果對照

| 根因 | 情境 | 可能形成的弱點 |
| --- | --- | --- |
| 人為假設 | 相信使用者只會上傳圖片 | 不受限制的檔案上傳 |
| 軟體錯誤 | 將輸入直接拼接到查詢 | SQL injection |
| 系統複雜度 | 整合時遺漏管理 API 設定 | 管理功能意外公開 |
| 過度客製化 | 自製且難維護的登入機制 | 弱驗證、帳號接管 |
| 技術／設計缺陷 | MFA 前發出完整 session | MFA bypass |

修補單一程式碼位置可以消除眼前弱點；找出根因則能避免相同問題在其他功能重複出現。

## 十、滲透測試人員的有效思維

### 1. 值得培養的習慣

- **理解系統：**先釐清元件、角色、正常流程、資料和信任邊界，再決定測試方法。
- **注意細節：**比較不同帳號、狀態和輸入下的細微回應差異。
- **保持好奇：**持續問「如果順序不同、角色不同、值在邊界外會如何？」
- **優先關注關鍵區域：**先測驗證、授權、敏感資料與高業務影響功能。
- **情境化思考：**同一弱點在不同資產上的實際後果可能完全不同。
- **創意思考：**思考弱點如何組合，但仍遵守範圍與安全限制。
- **驗證假設：**將觀察、推論和已證實事實分開記錄。

### 2. 應避免的思維

| 無效行為 | 問題 | 改善方式 |
| --- | --- | --- |
| Rushing to exploitation | 未理解系統便攻擊，容易漏測或中斷服務 | 先建立模型並使用低影響驗證 |
| Ignoring context | 只報技術現象，無法說明重要性 | 連結資料、角色和業務流程 |
| Over-reliance on tools | 自動結果可能誤報，也找不到邏輯漏洞 | 手動驗證並理解工具原理 |
| Making assumptions | 猜測行為而不驗證 | 記錄假設並設計可重複測試 |
| Tunnel vision | 卡在單一功能，犧牲整體涵蓋 | 使用時間盒並定期回顧覆蓋率 |
| Blindly following a checklist | 完成表格卻忽略情境特有風險 | 以清單保底，再以威脅模型延伸 |

課程題目中，「未理解功能或系統如何運作便開始攻擊」稱為 **Rushing to exploitation**。

## 十一、專案執行的最佳實務

### 1. 維護良好筆記

良好筆記能重現發現、避免重複工作並支援報告。每次重要測試可記錄：

```text
時間（含時區）：
測試人員：
資產／環境：
帳號與角色：
前置條件：
執行動作：
預期結果：
實際結果：
證據編號：
影響與後續：
是否已清除測試資料：
```

不要在一般筆記中保存明文正式密碼、完整 token 或未遮蔽個資。祕密和敏感證據應存於專案核准的加密位置並限制存取。

### 2. 蒐集證據

- 截圖需包含足以證明資產、角色和結果的資訊，但遮蔽無關敏感資料。
- 保存必要的請求／回應、日誌或工具輸出，並標示時間和測試條件。
- 只取得證明影響所需的最少資料，不因「報告更有說服力」而大量下載客戶資料。
- 證據要能讓另一位合格人員依步驟重現，而不是只有結論。

### 3. 管理時間與覆蓋率

- 先依高價值資產和高衝擊功能分配時間。
- 對不確定方向設定 timebox，到時重新評估是否繼續。
- 每日比較已測區域和範圍清單，避免最後才發現關鍵功能未測。
- 邊測邊整理證據與報告，保留結束前的品質檢查和清理時間。

### 4. 主動溝通

定期更新完成項目、接下來的計畫、覆蓋風險和阻礙。重大弱點、服務異常、範圍疑問或憑證失效不應拖到最終報告才提出。主動溝通可以讓客戶及時提供支援或調整優先順序。

課程題目中，避免 blocker 影響測試涵蓋程度的最佳實務是 **Proactive communication**。

### 5. 保持專業

- 尊重客戶人員，不把弱點歸咎於個人。
- 對不確定結果清楚標示限制，不誇大影響。
- 依資料分類要求保存和傳輸證據。
- 承認錯誤並立即通報可能造成的影響。
- 報告聚焦可修正的系統與流程，而非展示測試人員技巧。

課程題目中，有助於日後重現發現的做法是 **Maintaining good notes**。

## 十二、倫理、權限與信任

### 1. Ethics（倫理）

倫理要求測試人員在技術上「做得到」時，仍判斷「是否應該做」。實務行為包括：

- 遵守授權邊界，避免對範圍外資產採取行動；
- 避免不必要的中斷和不可逆變更；
- 只存取證明影響需要的最少敏感資料；
- 意外接觸高度敏感或範圍外系統時停止並回報；
- 在證據與報告中遮蔽不必要的敏感資料。

### 2. Permission（權限／許可）

正式測試開始前必須取得書面授權並確認清楚範圍。在可能中斷服務的操作前，要再次確認時窗和允許方法；對資產或行動是否在範圍內有疑問時，應向指定聯絡人澄清。

課程題目中，定義滲透測試邊界的是 **Scope**。

### 3. Trust（信任）

客戶把敏感系統和資料交給測試人員評估，信任必須透過持續行動建立：

- 定期提供真實而清楚的進度；
- 坦白限制、阻礙、誤差與不確定性；
- 準確呈現證據，清楚說明 **business impact**；
- 提供可以執行、符合客戶情境的修補建議；
- 迅速處理客戶疑慮，並依技術或非技術受眾調整溝通方式。

課程題目中，發現必須清楚呈現的影響是 **Business impact**；為避免意外揭露，報告應移除或遮蔽 **Sensitive data**。

### 4. 遇到意外情況的 STOP 原則

可用以下口訣協助處理超出預期的情況：

1. **Stop：**停止可能擴大影響的動作。
2. **Take notes：**記錄時間、操作、結果與已知影響，不擅自清除證據。
3. **Obtain guidance：**聯絡 RoE 指定窗口，說明事實並取得下一步指示。
4. **Proceed only when approved：**只有得到適當核准後才繼續或進行復原。

## 十三、一份高品質發現應包含什麼？

### 1. 建議結構

1. **標題：**精確描述弱點與受影響功能。
2. **摘要：**用非工具導向的方式說明問題。
3. **受影響資產：**列出經確認的主機、端點、版本或角色。
4. **嚴重度與理由：**分別說明可能性、衝擊與前置條件。
5. **重現步驟：**採最少、可重複且已去除祕密的步驟。
6. **證據：**必要的請求／回應或截圖，並遮蔽敏感資料。
7. **業務影響：**誰的什麼資料或流程會受到何種影響。
8. **修補建議：**提供根因導向、可執行且有優先順序的建議。
9. **參考資料：**內部標準或可信技術參考。
10. **修補驗證：**記錄重測日期、方法、結果與殘餘風險。

### 2. 好與不好的描述

**不足：**「掃描器發現高風險 SQL injection，請立刻修。」

**較完整：**「一般使用者可控制報表篩選參數，後端將其直接拼接至資料庫查詢。經低影響方式驗證，可讀取超出該角色權限的客戶記錄。建議改用參數化查詢、限制資料庫帳號權限，並檢查其他使用相同查詢元件的端點。」

完整描述把資產、角色、根因、已驗證影響和修補方向連在一起，也避免只複述工具名稱。

## 十四、課程畫面題目答案整理

| 題目重點 | 答案 | 理由 |
| --- | --- | --- |
| Penetration testing 的常見縮寫 | **Pentesting** | 課程採用的簡稱 |
| 誰追求廣泛覆蓋並評估系統多個區域？ | **Penetration Tester** | 測試人員依範圍系統性評估 |
| 誰專注最快的成功路徑？ | **Attacker** | 惡意攻擊者通常以目標達成為優先 |

| 登出後 Cookie 仍有效屬於哪個領域？ | **Session Management** | 工作階段未正確失效 |
| 修補已回報的高嚴重度問題屬於哪個風險階段？ | **Mitigation** | 正在降低風險 |

| 什麼做法有助於日後重現發現？ | **Maintaining good notes** | 保存步驟、條件與證據 |
| 什麼做法可避免 blocker 影響涵蓋程度？ | **Proactive communication** | 及早取得協助並調整計畫 |
| 什麼定義測試邊界？ | **Scope** | 指定允許的資產、時間和方法 |
| 發現應清楚呈現哪種影響？ | **Business impact** | 讓利害關係人理解優先順序 |
| 報告要移除什麼以避免意外揭露？ | **Sensitive data** | 遵守資料最小化與保密原則 |

## 十五、考前速記

### 一句話記憶

- **Pentest：**有書面授權、有範圍、可歸責、會報告與清理。
- **Web 五大面向：**驗證、授權、Session、輸入輸出、安全設定。
- **External vs. Internal：**外部看公開攻擊面；內部假設已有立足點並測橫向影響。
- **弱點／威脅／風險：**可被利用的缺口／可能利用缺口的來源／成功後的可能損害。
- **風險循環：**識別 → 分析 → 降低 → 監控。
- **根因五類：**人為假設、軟體錯誤、系統複雜、過度客製、設計缺陷。
- **好心態：**先理解、看細節、問如果、看情境、重證據。
- **遇到邊界不明：**停止、記錄、詢問、核准後再做。

### 容易混淆的配對

- Authentication 是「你是誰」；Authorization 是「你能做什麼」。
- Session fixation 是登入前後沿用攻擊者已知的識別值；session invalidation 是登出或停權後舊工作階段是否失效。
- Severity 描述技術嚴重程度；Risk 還要納入資產情境、可能性和業務衝擊。
- Mitigation 是降低風險；Acceptance 是經負責人知情核准後承擔殘餘風險。
- Coverage 是依計畫涵蓋多個區域；成功取得單一路徑不代表測試完整。

## 十六、自我檢查題與參考答案

### 題目

1. 為什麼滲透測試使用和攻擊者相似的工具，仍不等於惡意入侵？
2. 客戶只授權 `example.com`，測試中發現資料連到第三方服務時應怎麼做？
3. 一般使用者可以變更 URL 中 ID 看到其他人的訂單，主要屬於哪個 Web 測試領域？
4. 為什麼前端 JavaScript 的輸入檢查不能取代伺服器端驗證？
5. 外部和內部網路滲透測試的起始視角有何不同？
6. 一個弱點是否必然等於高風險？
7. 修補漏洞後，為什麼還需要 Monitoring？
8. 過度依賴自動工具可能遺漏哪些問題？
9. 發現範圍外敏感資料時，應如何處理？
10. 一份發現若只有截圖和「高風險」標籤，還缺少哪些資訊？

### 參考答案

1. 專業滲透測試有系統擁有者的書面授權、明確範圍、風險限制、資料處理規則、問責和報告義務；工具本身不能決定合法性。
2. 停止對第三方資產採取動作，保存最低限度觀察，依 RoE 通知客戶並確認資產所有權；只有完成範圍變更和適當授權後才能繼續。
3. Authorization，具體來說是水平存取控制問題，因為同權限使用者能存取其他使用者的物件。
4. 攻擊者可以直接修改或重送 HTTP/API 請求，完全繞過前端程式碼；安全決策必須由可信任的伺服器端執行。
5. 外部測試模擬幾乎沒有內部資訊或存取權的網際網路使用者；內部測試常假設已有內部端點或低權限帳號，評估提升權限和橫向移動風險。
6. 不必然。風險還取決於可達性、威脅能力、利用條件、資產價值、資料敏感性、既有控制與可能影響。
7. 修補可能不完整、設定可能再次漂移，環境與威脅也會改變；監控和重測用來確認控制持續有效。
8. 業務邏輯、角色和流程錯誤、弱點鏈、環境特有信任關係，以及需要理解回應差異的問題。
9. 立即停止可能擴大存取的操作，不額外下載資料，記錄必要事實並使用緊急聯絡路徑通報；依客戶指示處理證據。
10. 至少還需受影響資產、角色與前置條件、可重現步驟、已驗證影響、可能性與嚴重度理由、根因、修補建議和證據處理說明。

| Session | 工作階段 | 維持使用者登入狀態的機制 |
| Vulnerability | 弱點／漏洞 | 可能遭利用的缺口 |
| Threat | 威脅 | 可能利用弱點造成傷害的來源 |
| Risk | 風險 | 威脅利用弱點後的可能損害 |
| Likelihood | 可能性 | 風險事件發生的機會 |
| Impact | 衝擊 | 事件發生後的結果與損失 |
| Mitigation | 風險降低 | 降低可能性或衝擊的措施 |
| Residual risk | 殘餘風險 | 控制實施後仍存在的風險 |
| Finding | 發現事項 | 經驗證並提交給客戶的安全問題 |
| Evidence | 證據 | 支持發現且可供重現的資料 |
| Business impact | 業務影響 | 弱點對資料、營運、財務或聲譽的後果 |
